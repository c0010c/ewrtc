# 嵌入式纯 C WebRTC 库需求文档

- 文档版本：v0.5
- 更新日期：2026-09-25
- 当前阶段：第一阶段 x86_64 PoC 实现与验收
- 文档依据：本项目需求讨论中已确认的选择，以及随后提出的验证方案

本文将内容分为“已确认需求”“建议方案与默认值”和“待定事项”。已确认需求作为第一阶段范围基线；实际实现、已完成的浏览器互通测试、资源数据和剩余缺口记录在[验证记录](validation.md)。

## 1. 项目目标

开发适用于嵌入式 Linux 设备的轻量 WebRTC 音视频传输库，供设备业务程序通过 C 接口集成。设备发送视频和音频，并接收远端音频，实现实时观看及全双工语音对讲。

整体目标包含浏览器和原生 App 互通。第一阶段先在当前 x86_64 Linux 开发机上与 Chrome 完成技术验证，取得可重复的功能、稳定性和资源数据，为后续嵌入式设备适配提供依据。

“轻量”通过 SDK 及运行依赖体积、运行内存和 CPU 开销衡量。第一阶段先测量，再结合目标硬件制定资源上限。

| 核心库 | 会话管理、媒体协商、ICE/STUN/TURN、DTLS-SRTP、RTP/RTCP、编码媒体收发、视频重传、关键帧反馈、状态与必要统计 |

## 4. 第一阶段功能要求

### FR-01 会话生命周期

- 支持初始化、创建会话、建立连接、关闭及释放。
- 向业务报告连接状态和失败信息。
- 支持重复建立和释放会话；释放后的会话不再产生业务回调。
- 断网恢复后允许业务创建新会话并重新协商。第一阶段不要求无缝迁移或自动 ICE restart。

### FR-02 信令解耦

- 支持本地及远端 SDP、ICE 候选参数的输入输出。
- 核心库不绑定 MQTT、WebSocket 或具体云平台；业务自行传递信令。
- 项目提供最小信令示例，方便复现连接过程。

### FR-03 视频发送

- 接收业务提供的 H.264 编码帧和时间信息，完成媒体传输。
- 接收远端关键帧请求并通知业务，业务负责提供可用关键帧。
- 验证大帧分包、视频丢包重传和丢包后的画面恢复。

### FR-04 音频双向传输

- 支持同时发送和接收 Opus 编码音频。
- 接收音频通过回调交给业务处理。
- 第一阶段通过可识别的测试音频验证两个方向，不以收到数据包数量代替媒体有效性检查。

### FR-05 直连与中继

- 支持配置 STUN/TURN 地址及 TURN 凭据。
- 优先尝试直连，并允许选择 TURN/UDP 中继路径。
- 测试能够强制使用中继，并记录实际选中的连接路径，证明中继能力可用。

### FR-06 基础弱网与缓存

- 支持处理视频 NACK 重传请求及关键帧反馈。
- 发送队列与重传缓存必须有界；容量不足时向业务提供明确的错误或背压信息。
- 验证丢包、延迟及断网恢复场景，记录重传、缓存占用和媒体恢复情况。
- 第一阶段不实现完整的带宽估计与外部编码器动态码率控制闭环。

### FR-07 可观测性

- 提供完成验收所需的状态、错误、发送接收流量、重传和缓存统计。
- 结合 Chrome 统计和测试工具，记录丢包、实际网络路径、连接耗时和首帧耗时。
- 明确指标来源和统计口径，区分库内统计与端到端观察结果。

## 5. 验收场景

| 场景 | 验收内容 |
| --- | --- |
| 依赖与构建 | 设备端 SDK 及运行依赖符合 C 语言约束；可以脱离特定云信令独立运行 |
| H.264 互通 | 两档参考负载均可在 Chrome 正常显示，持续推进画面 |
| Opus 全双工 | Chrome 播放设备侧测试音频，同时向 C 端发送测试音频；接收结果可解码并识别内容 |
| UDP 直连 | 建立连接并传输媒体，确认实际路径为直接连接 |
| TURN/UDP | 强制中继后仍能传输音视频，并以连接统计或服务端记录确认路径 |
| 丢包重传 | 在受控丢包下观察并验证 NACK 与实际重传行为 |
| 关键帧恢复 | 关键帧请求到达业务回调，业务提供关键帧后画面能够恢复 |
| 缓存压力 | 队列达到上限时行为明确，内存不因持续积压而无界增长 |
| 断网恢复 | 断网后能报告状态变化；网络恢复并重新协商后能够恢复媒体传输 |
| 生命周期 | 反复连接、关闭和释放，无崩溃、死锁或可确认的持续泄漏 |
| 错误输入 | 非法参数、无效状态调用及媒体输入异常返回明确结果，不导致崩溃 |

以下数值来自前轮方案，作为建议的首轮测试配置，尚不属于已确认的产品质量指标：

- 两档视频负载分别连续传输 30 分钟。
- 建立与释放会话循环 100 次。
- 分别测试 1% 和 5% 丢包，并增加受控延迟场景；报告应记录延迟、抖动、带宽和丢包作用方向。
- 诊断构建执行内存检查；Release 构建用于资源测量，两类结果分别记录。

第一阶段记录弱网下的卡顿及恢复表现，不预设未经验证的流畅度、延迟或连接成功率承诺。

## 6. 资源测量口径

| 指标 | 测量要求 |
| --- | --- |
| 体积 | 分别记录 SDK 本体与运行依赖，给出完整运行所需体积；注明静态/动态链接和调试符号处理方式 |
| 内存 | 区分初始化后空闲、建连、稳定传输和断开释放阶段，记录基线与峰值 |
| CPU | 两档负载分别测量；注明 CPU 型号、采样时长及百分比计量方式 |
| 线程与缓存 | 记录线程数量、缓存配置和实际占用，帮助后续嵌入式适配 |
| 时延 | 记录连接耗时、首帧耗时和恢复耗时，并说明各项计时的起止事件 |
| 可复现性 | 记录上游版本、依赖版本、编译选项、Chrome 版本、素材参数和网络条件 |

采集、编解码、测试页面和外部服务的开销单独统计。若测量进程包含示例代码或素材缓冲，应注明其贡献，避免将进程总开销直接称为库自身开销。

当前 x86_64 主机的测量数据用于建立基线，目标嵌入式设备确定后需要重新测量。

## 7. 建议实现方案与默认值

用户已确认采用基础纯 C 组件自行实现 WebRTC 会话与媒体层，并明确排除 AWS WebRTC C SDK。PoC 同时实现自有 ICE 与 libjuice，以及 OpenSSL 与 Mbed TLS 两种 DTLS 后端。PoC 可在会话创建时选择后端，产品构建可裁剪未选用的后端。

### 7.1 组件与后端

- 自有 ICE 后端与 libjuice 后端均需通过 IPv4/UDP 直连、TURN/UDP 和断网重建验收。自有后端覆盖候选检查、角色冲突、持续授权与 TURN 分配、权限、续期。
- OpenSSL 和 Mbed TLS 后端均需完成 DTLS-SRTP 协商、证书指纹校验和密钥导出；libSRTP 负责 RTP/RTCP 保护。
- 共用层自行实现 Chrome offer 到设备 answer 的 SDP 协商、H.264/Opus RTP、RTCP、NACK/RTX 和 PLI/FIR 处理。
- 锁定上游提交和依赖版本，检查最终链接产物；设备端及运行依赖不能含 C++。
- 当前上游 Google WebRTC 源码仅供参考，不作为设备端运行依赖。

### 7.2 接口与协商建议

- 对外使用不透明会话句柄、配置结构、媒体输入接口、事件回调和统计查询。
- 视频输入建议为完整 H.264 Annex-B 编码帧，附时间戳及关键帧标记；音频输入建议为独立 Opus 编码包，附时间信息。
- 首轮由 Chrome 发起协商，设备侧回答，并支持增量交换 ICE 候选。
- 缓存满时建议返回明确的背压错误；具体内存所有权、线程及回调约束在接口设计中固定。
- H.264 首轮限定 Constrained Baseline、无 B 帧，关键帧携带 SPS/PPS。
- SDK 内部使用 context 共享 I/O worker 和准备线程；libjuice 后端允许增加组件线程，实际线程数量纳入测量。
- 提供独立 WebSocket 信令示例。浏览器页面和外部测试工具使用适合其运行环境的语言；纯 C 约束针对设备端 SDK 及其运行依赖。

### 7.3 测试素材建议

- H.264：无 B 帧，约两秒一个关键帧；720p30/约 1Mbps 和 1080p30/约 2Mbps。
- Opus：48kHz、单声道、20ms 分包。
- 素材按时间戳实时发送，循环播放时保持时间线合理连续。
- 素材发送示例需要能够响应关键帧请求，保证后续帧依赖和时间线有效。
- Chrome 发送可重复的测试音频；C 端接收后通过外部工具离线解码校验。

## 10. 模块化与 PAL（已确认并实施）

SDK 内部组件独立构建、测试和组合；安装包只公开业务与平台适配接口，能力范围不扩大。拆分协议层、媒体层和 Session，平台能力通过按实例注入的 PAL 隔离，当前提供 Linux 实现。内存分配和日志可以由业务接管，第三方内部的平台依赖由相应后端负责。底层组件由调用方驱动，完整 SDK 使用 context 共享调度，平台服务由应用向 context 显式注入；TURN 独立为内部组件，native ICE 持有 socket、TURN 借用。Media 保持一个内部组件，Session 内部按运行时、连接和统计拆分；内部事件投递失败必须报告并结束会话。尚未发布，不提供兼容包装或迁移说明。

详细边界和迁移方式见[模块架构](modular-architecture.md)，本轮实测结果见[模块化验证](modular-validation.md)。原验证记录保留为重构前基线，不代表新代码已通过相同检查。
